1The question, and eight tracks that answer it

The final project is a small research study in natural language processing. You choose one question, build a working baseline, and test one targeted change under a fixed budget. The deliverables are a poster presentation, a research report, and reproducibility materials. What is graded is not the size of the system but the clarity of the question, the fairness of the comparison, and the honesty of the write-up: a project that shows one clean success and one well-explained failure is a good project.

AI coding tools have changed what a four-week project can be. A team can now stand up a 3D scene, a game, a training run, a dataset pipeline or an agent harness in days instead of weeks. We therefore ask every team the same thing: what can you learn in a month that you could not learn without doing the experiment? The PDF guide's appendices and the Lecture 8 topics are merged into the eight tracks below, ordered from the most popular and easiest to understand to the more specialised, with competitions and entrepreneurship last. Tracks are entry points, not fences: a campus NPC project is Track C but borrows memory designs from Track A and evaluation discipline from Track D. Where the briefs come from

Each track starts from published work that a team can extend in four weeks; every brief links to its papers, code and data, and the PDF guide lists them as references. Track A builds on executable agent benchmarks such as SWE-bench and MLE-bench, and on agents that write surveys (AutoSurvey). Track B asks for small, testable changes to post-training in the spirit of selective token training (Rho-1), reinforcement learning on high-entropy tokens and simplified policy optimisation (DAPO, Dr. GRPO). Track C draws on generative agents, egocentric assistants (EgoLife), embodied question answering (OpenEQA), and courses and lecture videos generated by AI (MAIC, Paper2Video). Track D builds on rubric-based evaluation (HealthBench), long multimodal context (LongLLaVA, MileBench) and audits of which model an API really serves (model equality testing, Real Money, Fake Models). Track E follows audits such as the dialect-prejudice study in Nature; Track F starts from speculative decoding and the alignment of a draft model with its target (EAGLE-3, DistillSpec), and from engines that stream a trillion-parameter mixture of experts from disk on a single CPU (kimi-k3-in-c); Track H from open tutoring systems (DeepTutor) and the evidence that unguarded AI help can harm learning.

AAgents & harness: tools, skills & iterative repair

Lecture 7 framed an agent as model + harness. This track is about the harness: the loop that runs the model's output, observes what happened (compiler errors, failing tests, a rendered frame, a simulator measurement, a sealed grader), and feeds that evidence back. The question is almost always the same: at a matched budget, does a loop that sees executable feedback beat one-shot generation or independent sampling, and what does each success cost? Because the model is usually an API call, this track is the most accessible on the page; the engineering effort goes into isolation, replay and scoring. Three 2026 additions: skills, reusable instruction folders that any agent can load (brief A9); agents that do research, from writing a survey to running a sealed self-improvement loop (A10, A5); and an ML-engineering agent that enters a Kaggle competition on its own and is scored by the leaderboard (A11).

What "matched budget" means here Fix the number of model calls, tokens, simulator evaluations or wall-clock time, and give the same budget to every condition. Report runtime separately. Run every artifact in a clean, isolated environment (a fresh container or browser context), and store the full generation trace so the comparison can be replayed.

Research questions this track asks

  • Which kind of feedback matters: error text, test results, rendered evidence, or a profiler trace? Which one gives the largest gain per extra call?
  • Does staged planning (plan, then build, then replay and repair) beat a direct build agent on executable realization, not just on code volume?
  • Can an agent revise a mechanism more successfully when it sees measured constraint violations than when it only sees "failed"?
  • Under a sealed evaluation, does iterative revision that keeps successful changes transfer to hidden data, or does it overfit the visible split?
  • How much of the quality–latency–cost frontier is reachable with test-time scaling alone (self-consistency, verifiers, search) before training anything?
  • When a tool call fails, what recovery policy (plain retry, typed error feedback, bounded repair) gives the best recovery rate per unit cost?
  • Does a packaged skill change what an agent produces on held-out tasks, and does the gain survive a change of agent or model?
  • When an agent writes a literature survey, which pipeline stage removes the most fabricated citations per unit of cost: retrieval, outlining, or a post-hoc checker?
  • On a Kaggle task, does tree search over solution drafts beat a greedy debug-and-improve loop at the same GPU budget, and does the agent's local validation score predict the private leaderboard?

More research questions in this area

  • Full replanning vs. local plan repair after a failed step: which keeps task success higher at the same call budget?
  • Robustness to DOM or UI changes and prompt injection for web agents: fix a task set, perturb the pages, measure success and side-effect rate (overlaps with D3).

Pitfalls we see every year The repair loop sees the held-out tests. The judge model wrote the code it judges. Budgets differ between conditions ("the loop just ran longer"). No isolation, so flaky runs are counted as failures. Reporting success rate without cost per success. Store traces; a reviewer should be able to replay any number in your table.

BTrain your own model: vertical models, new modalities, nanoGPT experiments & internals

This is the track for teams who want to touch weights. The philosophy is borrowed from Stanford CS336 and from Tang Jie's Advanced Machine Learning course at Tsinghua: to understand it, build it. A 0.1B–0.5B language model trained from random weights is now a one-GPU, one-week exercise, and post-training with SFT, DPO or GRPO fits in a Kaggle session (see Tutorial 2). Two newer directions make the track more interesting than "train a small GPT": weight-space programming (a frontier model reading and editing a checkpoint directly) and mechanistic interpretability at scale (do sparse-autoencoder features have consistent causal effects?). Whatever you choose, change one thing at a fixed budget and plot the learning curve. Three briefs added this term follow Lecture 8 directly: a nanoGPT speedrun experiment in architecture engineering (B10), a vertical model built with the Tutorial 2 recipe (B11), and a new modality such as speech, bio-signals or time series (B12). For post-training, B6 asks for a variant of your own (which tokens learn, which data, a cheaper PPO), not a reproduction.

Compute reality check A 0.1B model on 1–2B tokens trains in hours on one 24 GB GPU; 0.5B on a Chinchilla-style token budget needs several GPU-days. Establish throughput (tokens per second, peak memory) on the small model first, then decide whether the 0.5B run is affordable. Free tiers: Kaggle (about 30 GPU hours per week, T4/P100), Colab; paid by the hour: AutoDL and cloud providers. A report with a complete small-scale result beats an unfinished large one.

Research questions this track asks

  • At a fixed token budget, what does one data intervention (deduplication, quality filtering, a code-to-text mixture change) do to held-out loss and a downstream task?
  • Two model sizes at a matched approximate compute budget: which wins, and does the answer change with the data mixture?
  • Can a frontier model repair a specified failure by editing a checkpoint directly, with a bounded edit budget and no gradients? How does the patch compare with a random edit of the same size and norm?
  • Do SAE features that look interpretable on examples have a consistent causal effect across prompt templates, compared with random features and a neuron baseline?
  • Which small change to SFT or RL (which tokens receive gradient, which problems are sampled, how the loss is normalised, how much of PPO can be dropped) buys the most accuracy per GPU hour, and does the gain survive at large Pass@k?
  • How much does a domain-adapted model forget, and does a small replay mixture fix it?

  • For a vertical domain, which post-training stage (continued pre-training, SFT, preference optimization, retrieval) buys the most at a fixed GPU budget, and are retrieval and training substitutes or complements?

Generation is cheap; faithful, useful generation is not. Evaluation discipline Include unanswerable and ambiguous cases, so abstention can be measured. Collect a human baseline from five to ten classmates; a benchmark without one cannot say "easy for humans". Audit a random sample by hand and report agreement with the automatic metric. Never let the generator judge itself; if an LLM judge is unavoidable, use a different model and validate it against the audited sample. Check for contamination by asking each model to continue a truncated item. Keep intermediate logs replayable.

Part 2 · Datasets, corpora & evidence briefs D9–D14

Models come and go; a good dataset is cited for years. Lecture 8's fourth topic is dataset building, and each training stage wants a different artifact: documents for pre-training, instruction–response pairs for SFT, chosen/rejected pairs for preference optimization, prompts with verifiers for RL, trajectories for agents, rubrics for judges. This track also covers evidence: corpora whose every passage has provenance (source, date, version, span), retrieval pipelines that can show their work, and corpora that AI helped construct and that a verifier checked. The output is a released dataset or corpus with a data card, a loader, a validation script, and one experiment that shows what it changes.

Data discipline Record the license of every source and respect it. Strip personal data and say how. Deduplicate against the evaluation sets you will use, and report the overlap you removed. Keep provenance per item (where it came from, which prompt or person produced it, which checks it passed). Write the data card before the experiment, not after. A dataset nobody can load is not a deliverable; a validator that rejects malformed rows is.

EAI for society: position papers, audits & interventions

AI is reshaping work, language, education and public services faster than the evidence can keep up. This track asks you to take a clear position on one question about that future and to back it with a measurement you ran yourself. The questions Lecture 8 raised are the ones below: does AI widen gender inequality; does it reduce the voice of minority languages and dialects; does it cut or extend the welfare of people with disabilities; does it leave the Global South behind; does it concentrate wealth or spread productivity? The deliverable can be a position or perspective paper in the style of the ICML and NeurIPS position tracks (a claim, the evidence for and against, the alternative views, and what should change), an audit study with a controlled design, or an intervention that measurably helps a group. All three are graded on the same thing: a falsifiable claim and an honest test of it.

What a position paper needs A one-sentence claim that someone could disagree with. The strongest version of the opposing view, stated fairly. Evidence from the literature, organised by theme rather than listed (the "related work is not a shopping list" rule from the writing tips). One piece of evidence you produced: an audit, a replication, a survey, a cost calculation. A concrete recommendation with who should act. ICML's position track asks reviewers to judge "is the argument well-supported and does it advance the discussion?", not "is the method novel?".

FEfficiency, serving, on-device & GPU kernels

Inference is where most of the compute in the world now goes, and it is a track where a single GPU and a careful measurement protocol produce publishable numbers. Projects here study a systems trade-off: kernel generation with feedback, scheduling short and long requests together, quantization, speculative decoding, or edge deployment. Fix the workload and the measurement protocol before comparing methods; report latency distributions, not averages; and check correctness on fresh inputs, because a fast wrong kernel is the most common result in this area (the KernelBench-Verified paper is required reading on why reported speedups often evaporate). Two additions this term: an on-device protocol for phones and laptops (brief F8), and an evolutionary, RSI-style loop that optimises your own kernel or configuration under a sealed test (F9). F6 now includes the extreme case of a memory budget: a 2.78-trillion-parameter mixture-of-experts model streamed from disk on a single CPU.

Measurement protocol Warm up, synchronize, repeat; report median and 95th percentile; pin the GPU clock or report its state; log the driver, CUDA and library versions; compare against both eager PyTorch and a compiled baseline where supported. Record power with nvidia-smi if you report energy. Keep the replay script in the repository.

Research questions this track asks

  • On a fixed KernelBench subset, does iterative repair with compiler, correctness or profiler feedback beat independent candidates at a shared generation budget, and how many results are both correct and faster than each baseline?
  • Which batched-token budget meets a stated time-to-first-token target at each request rate for a mixed short/long workload?
  • Under identical prompts, how do serving engines differ in throughput, p50/p95 latency and energy per token?
  • What accuracy does quantization or distillation cost on the tasks you care about, and where does it break first?
  • How does speculative decoding's acceptance rate, and therefore its speedup, vary across domains and draft models?
  • Can a real-time pipeline run on a laptop or phone with a bounded memory budget, and what is dropped to get there?
  • When a mixture-of-experts model is far larger than memory, which split between resident layers and an expert cache, and which prefetch policy, buys the most tokens per second per gigabyte of RAM?
  • On a phone, which runtime, quantization and drafting setting meets a stated latency target, and what does each cost in accuracy and energy?
  • When an evolutionary agent optimises a kernel or a serving configuration, how much of the measured gain survives a sealed held-out test, and what did it try to game?

F6An edge real-time pipeline with limited memory

🎮 playable demo🔥 2026 hot topic⭐ bonus questionon-devicelaptop / phone

Run a small model (ASR + LLM, or a VLM) on a laptop or phone under a stated memory budget and latency target. The research question is what to drop (precision, context, model size) and what it costs.

Bonus: how far can a memory budget stretch? kimi-k3-in-c runs the 2.78-trillion-parameter Kimi K3 on one CPU in portable C99, with no GPU and no BLAS. Only 16 of 896 experts fire per layer (about 104B active parameters), so the dense trunk stays in RAM while the 1.45 TB of routed 4-bit experts stream from an NVMe drive through an LRU cache with prefetching. The output is byte-identical from 8 GB of RAM (about 26 s per token) to 128 GB (about 6 s); only the clock changes, and its own measurements show that allocation beats capacity (at 128 GB, giving the trunk memory before the expert cache was worth 1.69×). Reproduce the idea on a mixture-of-experts model that fits your disk (OLMoE-1B-7B, Qwen3-30B-A3B), then test one policy of your own: frequency-based caching, prefetching the next layer's experts from the router, a different trunk/cache split, or lower-precision experts, and plot tokens per second against gigabytes of RAM.

Compareconfigurations under the same budget; for the bonus, LRU caching vs. your cache or prefetch policy at three or four memory budgets, on the same prompts, checking that the output stays identical.
Measureend-to-end latency, memory, accuracy on a fixed task set, battery or power if possible; for the bonus, resident cache hit rate, the share of wall-clock spent on disk reads, and tokens per second per GB of RAM.
Delivera runnable app and the trade-off table.

Two student companies from this lab show the scale that is possible: 薯塔AI, an AI study platform for Sino-foreign universities, had covered 60% of CUHK-Shenzhen undergraduates by April 2025 (3,579 registered on campus, 4,680 in total, 1,239 daily active users and about 2,900 AI answers a day) and is expanding to seven other universities; 网事, a tennis app by 朱宇轩, has served over a thousand players and saved them more than 5,000 hours. A startup project is still a course project: it needs real users, a controlled comparison, and a report. What changes is the evidence you collect: activation, retention, willingness to pay, and a business memo that survives a sceptical reader.

What counts as a research result here Two versions of your product on the same user tasks (onboarding A vs. B, retrieval over course materials vs. a generic model, free vs. paid tier), with the metric decided in advance. Ten user interviews written up with the Mom Test rules (ask about their life, not your idea). A unit-economics table: cost per active user per month (API tokens, hosting, support) against what they pay or would pay. A one-page business memo. The poster shows the comparison and the retention curve, not the logo.

AI startup basics what every founder in this track should be able to explain

🎯 Problem before product

Write the customer's problem in their words before touching a model. Interview ten people with the Mom Test rules: past behaviour, not opinions about your idea. The lab's successful teams started from a course they were failing and a sport they played.

📊 Business model canvas

Customer segments, value proposition, channels, revenue, cost structure, key activities and partners. The canvas or the Lean Canvas fits on one page; fill it in week 1 and again in week 4 and show what changed.

💰 AI unit economics

Cost per active user per month = tokens × price + hosting + human review. Compare with ARPU (average revenue per user) and CAC (acquisition cost). Gross margins of AI apps are lower than classic software because inference is a cost of goods; caching, small models and routing are product decisions.

🔒 The "wrapper" question

If the model vendor ships your feature tomorrow, what remains? Proprietary data, a workflow embedded in a customer's day, distribution (a campus, a hospital, a WeChat group), trust and brand, switching costs. Name your moat in one sentence or admit you have none yet.

📈 Product-market fit signals

Retention curves that flatten rather than decay to zero; organic referrals; users complaining when it breaks; the Sean Ellis test ("very disappointed" if it disappeared ≥ 40%). Vanity metrics: sign-ups, demo views, likes.

💵 Pricing

Per seat, per usage, per outcome, freemium. AI products are moving toward outcome and usage pricing because costs scale with use. Test one price with a real "buy" button even if you refund everyone; stated willingness to pay is not a measurement.

⚖ Compliance in China and abroad

Generative AI services facing the public in China fall under the 生成式人工智能服务管理暂行办法 (2023) and algorithm filing rules; personal data under PIPL; the EU AI Act for European users. Education and health products have extra rules. Write the one paragraph that says what applies to you.

🚀 Build fast, measure faster

Vibe-coding tools make a prototype a weekend's work; the scarce resource is users and the discipline to measure. Ship to 20 users in week 2, not 2,000 in week 4. Read Paul Graham's "Do things that don't scale" and the YC library.

Research questions this track asks

  • Does retrieval over a course's own materials beat a general model for a student tutor on correctness and on the student's willingness to return next week?
  • Can an AI seller raise conversion in a real small shop without raising refund or complaint rates, and which messages it sends make the difference?
  • When an agent runs a business end to end, which decisions does it get wrong first (pricing, inventory, promises to customers), and does a rule layer fix them without killing revenue?
  • Do simulated patients or interviewers improve a trainee's performance with real humans, or only their comfort with the simulator?
  • From a sentence to a playable game or a printable object: what fraction of prompts yields something usable, and what does a repair loop add per attempt?
  • Which onboarding, pricing or guardrail variant keeps more users after two weeks, at what cost per retained user?

5Research playbook

Experiment design

Before writing anything, read the writing tips page (from Lecture 8): a report should read like a film with no dull stretch. Begin with one working baseline and one measurable outcome. Compare your method on the same held-out tasks and report the variables that affect interpretation: model version, prompts, training tokens, time limits, hardware, API spend. Include at least one comparison that isolates the main change, and show both a success and a failure with your explanation. A table of three numbers with seeds and a replay script is worth more than a page of screenshots.

  • One change. Everything else fixed: model, prompts, data, budget, seeds, evaluation code.
  • Matched budget. Same number of calls, tokens, simulator evaluations or training tokens per condition; wall-clock reported separately.
  • Held-out. A split (or scenarios, rooms, prompts, briefs) that nobody tuned on; frozen in week 1.
  • Independent checker. Executable tests, simulator state, ground truth, or a different model validated against a human-audited sample.
  • Seeds and variance. At least two seeds for anything stochastic; report the spread.
  • Negative result kept. If the change does not help, the error analysis is the contribution.
  • Replayable. Traces, logs and configs in the repository; one command reproduces the headline number.

Reproducibility checklist

  • Public GitHub repository with a README that states the question and the headline number.
  • Environment file and exact model versions (checkpoint hashes or API model IDs and dates).
  • Evaluation inputs, or a script that downloads them, plus the frozen held-out split.
  • The commands that reproduce the main table, and the replay script for any trace-based metric.
  • For competitions: the dated score or submission link and the notebook or bundle that produced it.

How to present at the poster session

  • Lead with the question and the comparison figure; the architecture diagram comes second.
  • Bring a live demo or a recorded replay on a laptop; have the failure case ready to show, not only the success.
  • Prepare a 90-second version and a 5-minute version of the story; posters are rated by other groups and TAs.

6FAQ

Can I work alone?

Yes. The suggested team size is two or three; a solo project should be scoped like one brief, not two.

Can we propose something that is not on this page?

Yes. Use the proposal template, name the closest track, and make sure there is a baseline, a held-out split and one change to test. The optional proposal exists for exactly this case.

Do we need a GPU?

Not for most briefs in Tracks A, C, D, E, G and H, which run on an API model plus a laptop (or a phone, for F8). Tracks B and F assume at least one GPU; Kaggle and Colab are enough for the small-scale version of every brief there.

Is a position paper (Track E) really a final project?

Yes, if it contains a falsifiable claim and at least one measurement you ran: an audit, a replication on current models, or a small survey. A literature review alone is not enough; a survey written by an agent and audited by you (brief A10) is.

Can a startup prototype (Track H) be our project?

Yes. Treat it as a product experiment: two variants on the same user tasks, a metric fixed in advance, real users, a cost table and a business memo. Keep user data minimal and consented.

Can we read the page in Chinese?

Yes: the 中文 button at the top right switches the text (links and citations stay in English). Deliverables are written in English.

How much API spend is reasonable?

Plan it in the proposal and report it in the paper. A matched-budget design keeps spend predictable; most projects fit in a modest budget because the held-out set is small and fixed.

Can we use AI coding agents to write the code?

Yes, and we expect you to. Describe material uses in the report, keep humans responsible for the experimental design and the claims, and verify generated code with tests.

Can we continue our own thesis or lab research?

Yes, if the four-week study is a clearly delimited piece with its own baseline and comparison, and you identify your own contribution versus prior work by you or collaborators outside the course.

Is a human user study required for Track C or E?

No. Scripted evaluations with a fidelity check and a transfer task are enough. If you do run a study, keep it small, anonymous and free of sensitive data, get consent, and describe the protocol in the report.

The competition ends after Dec. 25. Can we still use it?

Yes. Course deliverables follow the course schedule; report your local held-out results and add the public score when it exists.

What if our main change does not work?

Report it. A clean negative result with an error analysis and a working fallback experiment is a complete project. What fails a project is an unfinished baseline or a comparison that was never matched.

Will our report be public?

Reports are made public after the poster session unless you notify the teaching team. If you release the work later, please acknowledge the course.
