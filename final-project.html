1The question, and four ways to answer it

The final project is a small research study in natural language processing. You choose one question, build a working baseline, and test one targeted change under a fixed budget. The deliverables are a poster presentation, a research report, and reproducibility materials. What is graded is not the size of the system but the clarity of the question, the fairness of the comparison, and the honesty of the write-up: a project that shows one clean success and one well-explained failure is a good project.

AI coding tools have changed what a four-week project can be. A team can now stand up a 3D scene, a game, a training run, or an agent harness in days instead of weeks. We therefore ask every team the same thing: what can you learn in a month that you could not learn without doing the experiment? Pick a format below; all formats share the same schedule, deliverables and rubric.

AInteractive 3D worlds, embodied AI & digital humans

Language models are leaving the chat box. This track puts an LLM inside a 3D scene, a game, a robot simulator or an animated character, and asks what the language model actually contributes: spatial language, memory, grounded action, or interaction. Every project here ends in something you can play in a browser or watch as a replay, but the report is graded on the controlled comparison behind the demo. The 2026 toolchain makes the demo part cheap: image-to-3D models export glTF assets that three.js loads directly, open world models produce editable scenes, and a frontier coding agent can scaffold a three.js project in an afternoon. Spend the saved time on the evaluation.

Ground rules for 3D studies Start with one small environment and reuse assets. Hold out layouts, tasks or requests. Keep scene access identical between methods unless access itself is the variable. Score with a separate checker that reads simulator state, not with the model that acted. Record replays so a reader can see the failure, not just the number.

Research questions this track asks

  • Does state-aware retrieval of approved scene facts beat a static briefing for an NPC on held-out routes and dialogues, and at what latency?
  • When should a 3D assistant ask which object you mean instead of guessing? Does a trigger based on remaining plausible candidates beat always-ask and never-ask?
  • Does a typed action schema with a geometry checker reduce invalid placements and unintended edits compared with free-form scene edits?
  • Does question-guided camera control answer occluded questions with fewer observations than fixed or random exploration at the same action budget?
  • Does conditioning on audio plus a short style instruction improve beat alignment and blinded style preference over beat-matched retrieval?
  • Can a frozen manipulation policy be made robust to perturbations with a small adaptation or a recovery rule, without hurting the unperturbed case?
  • How should a speech assistant handle interruptions (barge-in) and memory so that task success rises without end-to-end latency exploding?

More research questions in this area

  • Viewpoint-dependent references. "The cup on my left" changes meaning with the camera. Measure how often a VLM resolves such references correctly from a fixed vs. a user-aligned view.

BAgents, generation & iterative repair

Lecture 7 framed an agent as model + harness. This track is about the harness: the loop that runs the model's output, observes what happened (compiler errors, failing tests, a rendered frame, a simulator measurement, a sealed grader), and feeds that evidence back. The question is almost always the same: at a matched budget, does a loop that sees executable feedback beat one-shot generation or independent sampling, and what does each success cost? Because the model is usually an API call, this track is the most accessible on the page; the engineering effort goes into isolation, replay and scoring.

What "matched budget" means here Fix the number of model calls, tokens, simulator evaluations or wall-clock time, and give the same budget to every condition. Report runtime separately. Run every artifact in a clean, isolated environment (a fresh container or browser context), and store the full generation trace so the comparison can be replayed.

Research questions this track asks

  • Which kind of feedback matters: error text, test results, rendered evidence, or a profiler trace? Which one gives the largest gain per extra call?
  • Does staged planning (plan, then build, then replay and repair) beat a direct build agent on executable realization, not just on code volume?
  • Can an agent revise a mechanism more successfully when it sees measured constraint violations than when it only sees "failed"?
  • Under a sealed evaluation, does iterative revision that keeps successful changes transfer to hidden data, or does it overfit the visible split?
  • How much of the quality–latency–cost frontier is reachable with test-time scaling alone (self-consistency, verifiers, search) before training anything?
  • When a tool call fails, what recovery policy (plain retry, typed error feedback, bounded repair) gives the best recovery rate per unit cost?

CGenerative AI for education & human–AI interaction

Generation is cheap; faithful, useful generation is not. This track takes a concrete piece of teaching material (a textbook passage, one math concept, one molecule, one physics law) and builds a workflow that turns it into something a learner can watch, rotate, or experiment with: an English skit, an explanation video whose narration follows the diagram, an interactive 3D biology or physics scene. The research question is about source fidelity (does the output stay true to the material?), interaction (does the system know when to ask?) and transfer (can the learner apply the idea to a new case?). Human studies are welcome but optional; a scripted evaluation with a transfer quiz is enough for a strong report.

How to evaluate education projects without a classroom Pair every generated artifact with (1) a fidelity check against the source (claims and target words mapped to passages), (2) a small blinded rubric for quality, and (3) a transfer task on new material (a new sentence, a new graph, a different protein chain). Measure learning as transfer, not as "engagement". If you do recruit classmates, keep it small, anonymous and free of sensitive data, and report the protocol.

Research questions this track asks

  • Does a plan that first maps each target word and factual claim to the source produce more faithful and more usable dialogues than a direct script prompt?
  • Does a structured storyboard that ties each narrated step to an equation and a visual event reduce narration–diagram mismatches in a math video?
  • Does giving the model the learner's selected 3D component and structure annotations improve the correctness and evidence of its answers?
  • Do typed simulator commands with trace-grounded explanations beat prompt-only interpretation for "change only the launch angle" requests?
  • When should a tutoring assistant ask a clarifying question? Does an ask-when-triggered policy beat always-ask and never-ask on task success and questions asked?
  • Do memory and reflection in an educational assistant change satisfaction or learning gain, or only the feeling of continuity?
  • What moderation design keeps an LLM-simulated class forum civil without flattening disagreement?

DTrain your own model: data, post-training & model internals

This is the track for teams who want to touch weights. The philosophy is borrowed from Stanford CS336 and from Tang Jie's Advanced Machine Learning course at Tsinghua: to understand it, build it. A 0.1B–0.5B language model trained from random weights is now a one-GPU, one-week exercise, and post-training with SFT, DPO or GRPO fits in a Kaggle session (see Tutorial 2). Two newer directions make the track more interesting than "train a small GPT": weight-space programming (a frontier model reading and editing a checkpoint directly) and mechanistic interpretability at scale (do sparse-autoencoder features have consistent causal effects?). Whatever you choose, change one thing at a fixed budget and plot the learning curve.

Compute reality check A 0.1B model on 1–2B tokens trains in hours on one 24 GB GPU; 0.5B on a Chinchilla-style token budget needs several GPU-days. Establish throughput (tokens per second, peak memory) on the small model first, then decide whether the 0.5B run is affordable. Free tiers: Kaggle (about 30 GPU hours per week, T4/P100), Colab; paid by the hour: AutoDL and cloud providers. A report with a complete small-scale result beats an unfinished large one.

Research questions this track asks

  • At a fixed token budget, what does one data intervention (deduplication, quality filtering, a code-to-text mixture change) do to held-out loss and a downstream task?
  • Two model sizes at a matched approximate compute budget: which wins, and does the answer change with the data mixture?
  • Can a frontier model repair a specified failure by editing a checkpoint directly, with a bounded edit budget and no gradients? How does the patch compare with a random edit of the same size and norm?
  • Do SAE features that look interpretable on examples have a consistent causal effect across prompt templates, compared with random features and a neuron baseline?
  • SFT vs. SFT + preference optimization on math or code: where does the extra stage help, and what does it cost?
  • How much does a domain-adapted model forget, and does a small replay mixture fix it?
  • How should a fixed LoRA parameter budget be allocated across layers?

EEfficiency, serving & GPU kernels

Inference is where most of the compute in the world now goes, and it is a track where a single GPU and a careful measurement protocol produce publishable numbers. Projects here study a systems trade-off: kernel generation with feedback, scheduling short and long requests together, quantization, speculative decoding, or edge deployment. Fix the workload and the measurement protocol before comparing methods; report latency distributions, not averages; and check correctness on fresh inputs, because a fast wrong kernel is the most common result in this area (the KernelBench-Verified paper is required reading on why reported speedups often evaporate).

Measurement protocol Warm up, synchronize, repeat; report median and 95th percentile; pin the GPU clock or report its state; log the driver, CUDA and library versions; compare against both eager PyTorch and a compiled baseline where supported. Record power with nvidia-smi if you report energy. Keep the replay script in the repository.

Research questions this track asks

  • On a fixed KernelBench subset, does iterative repair with compiler, correctness or profiler feedback beat independent candidates at a shared generation budget, and how many results are both correct and faster than each baseline?

  • Under identical prompts, how do serving engines differ in throughput, p50/p95 latency and energy per token?
  • What accuracy does quantization or distillation cost on the tasks you care about, and where does it break first?
  • How does speculative decoding's acceptance rate, and therefore its speedup, vary across domains and draft models?
  • Can a real-time pipeline run on a laptop or phone with a bounded memory budget, and what is dropped to get there?

FKnowledge, evidence, evaluation & safety

Can we trust what the model said? This track builds systems whose outputs carry a verifiable evidence chain (retrieved passage, document version, exact supporting span, verifier decision), and evaluations that can detect a specific failure: an unsupported claim, a stale document, a prompt injection, a text that was machine-written, a success that was claimed but not earned. Pick a concrete domain (medical guidelines, legal corpora, scientific reporting, customer service) and a concrete failure, and build the smallest pipeline that measures it.

Evaluation discipline Include unanswerable and ambiguous cases, so abstention can be measured. Audit a random sample by hand and report agreement with the automatic metric. Never let the generator judge itself; if an LLM judge is unavoidable, use a different model and validate it against the audited sample. Keep intermediate logs replayable.

Research questions this track asks

  • Does verifying each answer claim against a cited source span reduce unsupported answers at an acceptable cost in coverage?
  • Which component of an agentic RAG pipeline (query planning, retriever ensemble, draft-and-critic, citation repair) moves groundedness most, per unit of latency?
  • When should a system retrieve at all, and what happens with conflicting or stale sources?
  • Does a long-context evaluation that mixes "needle" retrieval with multi-step reasoning expose failures that needle tests alone miss?
  • Do combined defenses (input sanitization + sandbox + policy model) reduce prompt-injection success in a web agent without blocking legitimate tasks?
  • How separable are human-written, LLM-generated and LLM-refined texts, and which features survive a change of generator?
  • Can a system tell whether an AI-written scientific statement faithfully reflects the evidence it cites?

6Research playbook

Experiment design

Begin with one working baseline and one measurable outcome. Compare your method on the same held-out tasks and report the variables that affect interpretation: model version, prompts, training tokens, time limits, hardware, API spend. Include at least one comparison that isolates the main change, and show both a success and a failure with your explanation. A table of three numbers with seeds and a replay script is worth more than a page of screenshots.

  • One change. Everything else fixed: model, prompts, data, budget, seeds, evaluation code.
  • Matched budget. Same number of calls, tokens, simulator evaluations or training tokens per condition; wall-clock reported separately.
  • Held-out. A split (or scenarios, rooms, prompts, briefs) that nobody tuned on; frozen in week 1.
  • Independent checker. Executable tests, simulator state, ground truth, or a different model validated against a human-audited sample.
  • Seeds and variance. At least two seeds for anything stochastic; report the spread.
  • Negative result kept. If the change does not help, the error analysis is the contribution.
  • Replayable. Traces, logs and configs in the repository; one command reproduces the headline number.

Reproducibility checklist

  • Public GitHub repository with a README that states the question and the headline number.
  • Environment file and exact model versions (checkpoint hashes or API model IDs and dates).
  • Evaluation inputs, or a script that downloads them, plus the frozen held-out split.
  • The commands that reproduce the main table, and the replay script for any trace-based metric.
  • For competitions: the dated score or submission link and the notebook or bundle that produced it.

  • Lead with the question and the comparison figure; the architecture diagram comes second.
  • Bring a live demo or a recorded replay on a laptop; have the failure case ready to show, not only the success.
  • Prepare a 90-second version and a 5-minute version of the story; posters are rated by other groups and TAs.

7FAQ

Can I work alone?

Yes. The suggested team size is two or three; a solo project should be scoped like one brief, not two.

Can we propose something that is not on this page?

Yes. Use the proposal template, name the closest track, and make sure there is a baseline, a held-out split and one change to test. The optional proposal exists for exactly this case.

Do we need a GPU?

Not for most briefs in Tracks A, B, C and F, which run on an API model plus a laptop. Tracks D and E assume at least one GPU; Kaggle and Colab are enough for the small-scale version of every brief there.

How much API spend is reasonable?

Plan it in the proposal and report it in the paper. A matched-budget design keeps spend predictable; most projects fit in a modest budget because the held-out set is small and fixed.

Can we use AI coding agents to write the code?

Yes, and we expect you to. Describe material uses in the report, keep humans responsible for the experimental design and the claims, and verify generated code with tests.

Can we continue our own thesis or lab research?

Yes, if the four-week study is a clearly delimited piece with its own baseline and comparison, and you identify your own contribution versus prior work by you or collaborators outside the course.

Is a human user study required for Track C?

No. Scripted evaluations with a fidelity check and a transfer task are enough. If you do run a study, keep it small, anonymous and free of sensitive data, and describe the protocol.

The competition ends after Dec. 25. Can we still use it?

Yes. Course deliverables follow the course schedule; report your local held-out results and add the public score when it exists.

What if our main change does not work?

Report it. A clean negative result with an error analysis and a working fallback experiment is a complete project. What fails a project is an unfinished baseline or a comparison that was never matched.

Will our report be public?

Reports are made public after the poster session unless you notify the teaching team. If you release the work later, please acknowledge the course.
